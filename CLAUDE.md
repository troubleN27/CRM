# Офис-CRM

Внутренний сайт веб-студии из Кремниевой долины: сотрудники, клиенты, заявки, план офиса, учёт прихода/ухода, местоположение сотрудников, отчёты в Excel.

- Что делаем и для кого — [PRD.md](PRD.md)
- Как устроено (данные, страницы, статусы, отчёт, API агента) — [SPEC.md](SPEC.md)

## Доступ (решения заказчика)
- **План офиса** видят все, **карту города** с местоположением — только администратор.
- **ИИ-агент** работает через MCP-сервер (`mcp-server/`, вход по `MCP_SECRET_KEY`), который ходит в `/api/agent/*` по ключу `AGENT_API_KEY`. Агент читает данные и (решение от 26.10.2026) может **только одно изменение** — назначить заявку свободному сотруднику в офисе; каждое назначение пишется в AuditLog с `actorLabel: "ai-agent"`. Координаты, пароли и email учётных записей агент не получает. Новые изменяющие возможности агенту — только по явному запросу.
- **Отметки исправляет только администратор**: причина обязательна, каждое исправление пишется в журнал (AuditLog).

## Разделы сайта

1. **Сотрудники** — список, карточка, должность, контакты, рабочее место, текущий статус.
2. **Клиенты** — список компаний, контактные лица, история заявок.
3. **Заявки** — от клиента; поля: клиент, описание, адрес (с точкой на карте), исполнитель, статус (новая / в работе / выполнена / отменена).
4. **План офиса** — схема с рабочими местами; на месте видно, кто сидит и его статус (цветом).
5. **Отметка** — кнопки «Пришёл» и «Ушёл» (с выбором причины).
6. **Где сотрудники** — план офиса (кто в офисе) + карта города (кто вне офиса).
7. **Отчёты** — выгрузка в Excel за период: приходы, уходы, опоздания, отработанное время, выезды.

## Правила учёта времени (важно — не менять без запроса)

### Статусы сотрудника
- `OFF_WORK` — **не на работе** (рабочий день не начат или завершён).
- `OUT_OF_OFFICE` — **вне офиса** (рабочий день идёт, но сотрудник вышел).
- `IN_OFFICE` — **в офисе**.

### Переходы
- «Пришёл»: `OFF_WORK` → `IN_OFFICE` (начало рабочего дня) или `OUT_OF_OFFICE` → `IN_OFFICE` (вернулся).
- «Ушёл» — **обязательно выбрать причину**:
  - `LUNCH` — обед → `OUT_OF_OFFICE`
  - `CLIENT_VISIT` — выезд на заявку → `OUT_OF_OFFICE` (можно привязать заявку)
  - `PERSONAL` — личное → `OUT_OF_OFFICE`
  - `END_OF_DAY` — конец дня → `OFF_WORK`, **рабочий день завершён**
- Новый рабочий день начинается только следующим «Пришёл» после «Конец дня».

### Опоздание
- Рабочий день начинается в **09:00**.
- Допуск **5 минут**: приход до **09:05:59** включительно — вовремя, с **09:06:00** — опоздание.
- Опоздание считается только по **первому** приходу за день.
- Время считается в часовом поясе офиса: **`America/Los_Angeles`** (настройка `OFFICE_TIMEZONE`). В БД всё хранится в UTC.
- Константы (`WORKDAY_START`, `LATE_GRACE_MINUTES`) — в одном месте: `src/lib/attendance/config.ts`.

### Обязательная отметка прихода
- Сотрудник и менеджер не видят разделы, пока не нажали «Я пришёл»: `requireUser` уводит на `/[locale]/check-in`. Новые страницы обязательно начинать с `requireUser` — иначе отметку можно обойти.
- Админ отмечается на главной без блокировки и видит, кто не отметился после 09:05.
- Логика — `src/lib/attendance/` (`time.ts` — опоздания и часы, `service.ts` — отметки), всё время — серверное.
- Проверить «после 09:05» днём по Ташкенту (в LA ночь): временно запустить с `OFFICE_TIMEZONE=Asia/Tashkent` в окружении, не меняя `.env`.

### MCP-сервер для агента
- Папка `mcp-server/` — отдельный пакет (`npm install` внутри неё). Корневые `tsconfig` и ESLint её не проверяют.
- Логика инструментов — на сайте (`src/lib/agent.ts`, `/api/agent/*`), MCP-сервер только вызывает API и пишет понятные сообщения (`mcp-server/src/app-client.ts`, `tools.ts`).
- Агент подключён через `.mcp.json` в корне; ключ — в переменной окружения `OFFICE_MCP_KEY`, на сервере — `MCP_SECRET_KEY` в `mcp-server/.env`. Ключи в файлы, которые попадают в Git, не писать.

### Позиции: одно общее место
- Все позиции (имитация, датчики, телефон) идут только в `POST /api/positions` → `recordPositions` в `src/lib/positions.ts`. Новый источник — новый `source`, а не новый эндпоинт.
- Ключ устройств — `POSITIONS_API_KEY` в `.env`.

### Местоположение (приватность)
- Координаты записываются **только между первым «Пришёл» и «Конец дня»**.
- При статусе `OFF_WORK` геолокация **не запрашивается и не сохраняется** — проверка на сервере, а не только в браузере.
- В офисе положение = рабочее место на плане; вне офиса — точка на карте города.
- Браузер спрашивает разрешение на геолокацию; если отказано — показываем «местоположение неизвестно», без ошибок.

## Языки
- **Русский (`ru`)** — по умолчанию, **узбекский (`uz`, латиница)**.
- Все тексты интерфейса — только в `messages/ru.json` и `messages/uz.json`, никаких строк прямо в коде.
- Новый ключ добавлять сразу в оба файла.
- Язык в URL: `/ru/...`, `/uz/...`; переключатель в шапке.
- Отчёт Excel — на языке пользователя, который его скачал.

## Структура проекта (план)

```
prisma/
  schema.prisma        # модели БД
  seed.ts              # вымышленные демо-данные
messages/ru.json, uz.json
src/
  app/[locale]/        # страницы
  app/api/             # API (отметки, геолокация, отчёты)

```

Бизнес-логику (статусы, опоздания, расчёт часов) держать в `src/lib` чистыми функциями и покрывать тестами Vitest.

## Секреты
- Пароли, ключи и строка подключения к БД — **только в `.env`**. Этот файл в `.gitignore` и **никогда не попадает в Git**.
- В Git лежит только `.env.example` с пустыми/примерными значениями.
- Не писать секреты в код, логи, сид-файлы и сообщения коммитов.
- Пароли демо-учёток берутся из `.env` (`DEMO_ADMIN_PASSWORD`, `DEMO_MANAGER_PASSWORD`, `DEMO_EMPLOYEE_PASSWORD`).
- Пароли пользователей хранятся только как bcrypt-хэш (`src/lib/password.ts`), открытый текст нигде не сохраняется и не логируется.

## Дизайн-система «Strict Dark» (обязательно)
- **Только токены:** `bg-canvas / surface / elevated / pressed`, `border-line / line-strong`, `text-fg / fg-2 / fg-3`, `brand / brand-fg / brand-ink`, `success / warning / danger / info` (+ `-bg`). Стандартная палитра Tailwind (`slate`, `blue`, `white`…) запрещена.
- **Запрещено:** градиенты, белый и любые цвета светлее `#A5ABB8`, размытые тени (`shadow-*`), жирное начертание (только 400 и 500). Глубина — ступенями фона и рамками 1px.
- **Числа, даты, ID** — класс `num` (Geist Mono + табличные цифры).
- **Радиусы:** `rounded` (4px) у полей и тегов, `rounded-md`/`rounded-lg` (6–8px) у контейнеров.
- **Движение:** микро-взаимодействия 150–200 мс, панели и страницы 300–450 мс, кривая `ease-out-soft` (cubic-bezier(0.22, 1, 0.36, 1)) или пружина; сайдбар — пружина 300/30. Всё уважает «уменьшить движение» (`MotionConfig reducedMotion="user"`, Lenis и GSAP отключаются).
- **Ожидание — скелетоны** (`.skeleton`, пульсация прозрачности 40–70%), без спиннеров.
- **Подтверждения** — не `window.confirm`, а `ConfirmSubmit` (окно растёт из кнопки) или двухшаговая кнопка.
- **Клавиатура:** всё доступно с Tab/Enter/Esc/стрелок; у новых списков — как в `DataGrid`.
- Общие классы — `src/components/ui.ts`; каркас — `src/components/shell/`; таблица — `src/components/grid/DataGrid.tsx`; карточка — `src/components/entity/EntityDrawer.tsx`.
- **Проверка:** `npm run design:check` — правила выше + контраст пар токенов ≥ 4.5:1. Перед сдачей изменений интерфейса — обязательно.
- Блоки с собственной прокруткой (карты, ленты, таблицы, доска) помечать `data-lenis-prevent`.

## План офиса
- Координаты мест и зон хранить **только долями 0…1 от размера картинки** (`src/lib/office-plan.ts`), никогда не пикселями — иначе места съезжают на другом экране.
- Загружаемые картинки: PNG, JPG, WebP до 5 МБ. Тип проверять по байтам, SVG от пользователей не принимать.

## Демо-данные
- **Все люди и компании вымышленные.** Не использовать реальные имена, телефоны, email, адреса известных людей и компаний.
- Email только на домене `example.com`, телефоны сотрудников вида `+1 555-01xx`, клиентов в Ташкенте — `+998 00 000-00-xx` (несуществующий код оператора).
- Клиенты демо — в Ташкенте: настоящие районы, вымышленные улицы («Примерная», «Тестовая»).
- Имена — смесь русских, узбекских и американских, явно придуманные.
- Точки на карте — в районе Пало-Альто / Маунтин-Вью (общие места, не чьи-то дома).

## Команды

```bash
npm install                   # установить зависимости
npm run db                    # запустить PostgreSQL (порт 5433, данные в .pgdata)
npm run db:migrate            # создать/обновить таблицы (+ демо-данные при первом запуске)
npm run db:seed               # пересоздать демо-данные
npm run dev                   # сайт на http://localhost:3000
npm test                      # тесты логики (Vitest)
npm run check:login           # проверить вход за 3 роли (сайт должен быть запущен)
npm run demo:today            # «рабочий день сейчас»: всем приход, трое вне офиса
npm run sim:on                # включить имитацию движения (каждые 3 с, лог — во временной папке системы)
npm run sim:off               # выключить имитацию
npm run sim:status            # работает ли имитация
npm run mcp                   # запустить MCP-сервер для агента (http://localhost:3100/mcp)
npm run mcp:check             # проверить MCP-сервер (сайт и MCP-сервер запущены)
npm run lint                  # проверка кода
npm run design:check          # правила дизайна Strict Dark и контраст токенов
npm run db:stop               # остановить PostgreSQL
```

**Не запускать `npm run build`, пока работает `npm run dev`:** сборка перезаписывает `.next`, и dev-сервер начинает бесконечно перезагружать страницы. Сначала остановить dev-сервер. По той же причине программы не должны писать в папку проекта файлы, которые меняются каждые несколько секунд (лог имитации лежит во временной папке системы).

Если `prisma migrate dev` отказывается работать без интерактивного режима (так бывает при предупреждениях о потере данных), миграцию можно сгенерировать командой `npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script` в `prisma/migrations/<дата>_<имя>/migration.sql`, а применить через `npx prisma migrate deploy`. Стирать базу (`migrate reset`) — только с явного согласия пользователя.

Роли: `ADMIN`, `MANAGER`, `EMPLOYEE`. Роль и активность сверяются с БД при каждом запросе (колбэк `jwt` в `src/auth.ts`), поэтому смена роли действует сразу. Права проверять на сервере через `requireUser(locale, roles)` из `src/lib/session.ts` (страницы) или через `auth()` (серверные действия).
Демо-логины: `admin`, `manager1`, `manager2`, `employee1` … `employee10`. Пароли — в `.env`.

## Как работать в этом проекте (для Claude)
- После каждого изменения **коротко и простыми словами** писать: **что сделано** и **как проверить** (какую страницу открыть, что нажать, что должно получиться).
- Перед изменением правил учёта времени — перечитать раздел «Правила учёта времени».
- Любое изменение схемы БД — через миграцию Prisma.
- Не добавлять платные сервисы и сервисы, требующие регистрации/ключей, без явного запроса.
